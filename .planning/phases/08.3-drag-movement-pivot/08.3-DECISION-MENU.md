## 2. The probe-proven mechanism at a glance (drag research RQ2)

The viable custom-wiring mechanism -- every ingredient probe-proven live
on this exact build (Windows PyMOL 2.5.0):

```python
# 1. ONE-TIME gesture map (at game activation; restore at cleanup):
cmd.button('left', 'shft', 'dgmv')   # shift-left-drag = translate the armed drag selection
#   optional extras: cmd.button('left', 'shft', 'dgrt')  # rotate (pick ONE of the two for shift-left)
#                    cmd.button('left', 'ctsh', 'dgmz')  # depth (toward/away viewer)
# 2. ON EVERY SUCCESSFUL PICK (end of do_pick, after the pk1 read):
cmd.select('_aam_drag_sele', obj)                    # selection-form name, NOT the object name
cmd.drag('_aam_drag_sele', wizard=0, edit=0)         # arm C-side drag; NO wizard install; NO mode switch
# 3. AT CLEANUP (Done/pop/replace):
cmd.drag()                                           # deactivate drag state
cmd.set('button_mode', saved_button_mode, quiet=1)   # profile-level restore
cmd.mouse()
```

Receipts (each a live probe and/or a file:line source citation):

- `wizard=0` avoids the Dragging wizard ENTIRELY: GameWizard stays
  top-of-stack and still receiving picks (probes C2/C3/C9) -- this closes
  the item ARCHITECTURE.md:169 flagged UNVERIFIED ("drag-under-custom-
  wizard behavior").
- `edit=0` skips the 3-Button-Editing button-profile switch (probe C8).
- The arm must use a SELECTION name, never the object name: a
  selection-form arm bakes coordinates via ObjectMoleculeTransformSelection
  (Editor.cpp:2275-2281) -- rigid, world-frame, detector-visible; an
  OBJECT-name arm takes the FORBIDDEN object-matrix branch
  (Executive.cpp:3208-3259) -- the Pitfall-6c identity-breaking path.
- ANY pick clears the armed drag state, so re-arm at the END of every
  do_pick (after the pk1 read -- EditorInactivate deletes pk1..pk4) is
  MANDATORY (probes 083B(1)(2)); double-arm is idempotent (083B(4)).
- No per-slot button read-back API exists, so save/restore is
  PROFILE-level `button_mode` -- the SAME story the stock Dragging wizard
  uses for itself (dragging.py:78-80); probe D2 proves the restore works.
- The C drag math IS our movement law's math: per motion event PyMOL
  applies the exact R^T camera-to-world conjugation that
  wizard_core.view_camera_to_world implements (drag RQ3; probe 083C).

## 3. THE GESTURE OPTIONS (drag research RQ7)

### OPTION A -- shift-left-drag (`cmd.button('left','shft','dgmv')`) -- RECOMMENDED

- Mapping: shift-left-drag = view-plane translate of the selected AA.
  Depth: Toward-ligand (always) + optional
  `cmd.button('left','ctsh','dgmz')` (ctrl+shift-left-drag = depth) as
  a sub-choice. Rotation: the existing 'Rotate 90 deg' panel button
  survives (`rotate_view(90)` -- centroid pivot, proven SMOKE-06/07);
  optionally ','/'.' keys survive (keyboard ROTATE, not direction keys --
  the locked decision removed only direction keys).
- Capabilities: full view-plane translate + 3D approach via Toward;
  optional depth trim; rotation via button/keys.
- Conflicts: sacrifices shift-left box-select-ADD (stock '+Box';
  box-subtract on shift-middle survives -- asymmetric). Box-select is not
  a gameplay verb; acceptable cost, but the user should confirm.
- Save/restore: profile-level (probe D2); erases any pre-game per-slot
  user customization (stock-parity limitation).
- Headless-testability: FULL (all of SMOKE-24 except feel).
- Feasibility verdict: HIGH -- every single mechanism probe-proven on
  this exact build (C1-C9, D1-D2, E1, 083B, 083C).

### OPTION B -- alt-left-drag (`cmd.button('left','alt','dgmv')`)

- Mapping: alt-left-drag = translate. Sacrifices alt-left camera pan -- a
  DUPLICATE of ctrl-left pan (controlling.py:333 vs :327), so net camera
  loss is zero on stock profiles.
- Capabilities: as Option A (depth sub-choice and rotation story the
  same).
- Conflicts/caveat: Alt-key interference on Windows/Qt (menu mnemonics,
  focus stealing) is REAL RISK and NOT headless-verifiable -- it needs a
  [HUMAN] Alt-delivery test at the 8.3 GUI checkpoint if chosen.
- Save/restore: profile-level, as A.
- Headless-testability: wiring half FULL; delivery half [HUMAN] (Alt
  behavior).
- Feasibility verdict: MEDIUM -- mechanism identical to A (probe-proven);
  the Alt delivery is the only unverified link.

### OPTION C -- stock Dragging-wizard sandwich (zero custom buttons)

- Mapping: none. The pick handler calls stock
  `cmd.drag(selection-form, wizard=1)`; the Dragging wizard pushes over
  GameWizard; the user drags with the auto-configured editing gestures;
  Done pops -> GameWizard auto-resumes (probe B1-B6).
- Capabilities: translate + rotate + depth (the full stock drag scheme),
  stock UX.
- Conflicts/hazards: the game panel is REPLACED mid-drag
  (Confirm/Toward/Reset invisible while dragging); requires editor
  scheme 3 (self-destructs to a no-op drag otherwise -- dragging.py:49-54;
  a mid-drag mode switch kills the wizard); stock whole-molecule drag
  defaults to the MATRIX path unless WE arm the selection form (at which
  point it is Option A's machinery anyway) -- using the matrix path as the
  primary movement input violates the baked-coordinates law.
- Save/restore: the stock Dragging wizard's own cleanup restores
  button_mode (dragging.py:72-80).
- Headless-testability: lifecycle FULL (B1-B6 probe pattern); feel
  [HUMAN].
- Feasibility verdict: MEDIUM-LOW as the primary input (panel takeover
  is hostile to the game loop); viable as an accessibility fallback or a
  debugging tool.

### OPTION D -- Qt event-filter raw drag (fully custom, literal ctrl+drag)

- Mapping: game_window.py installs an application-level Qt event filter;
  while a slot is selected and the chosen modifier is held over the
  viewer widget, mouse-move events are consumed and converted to
  `wizard.drag_move(dx_px, dy_px)` calls (our own RQ3 math + cmd.translate
  + assert per event); a second modifier routes to rotate_axis for
  drag-rotation.
- Capabilities: total control -- literal "ctrl+mouse movement upon
  selection" (the human's own words); per-event identity asserts; panel
  refresh per frame; arbitrary rotation gestures; nothing stock is
  remapped.
- Conflicts/hazards: deep coupling to PyMOL's internal GL widget
  (reaching it uses pymol.Qt internals -- fragile across builds); ZERO
  headless provability (Qt needs a display; every delivery step becomes
  [HUMAN]); an event-filter bug can hijack the whole viewer; must
  coexist with PyMOL's own mouse handling on the same widget.
- Save/restore: none needed (nothing stock is remapped).
- Headless-testability: the drag_move MATH half only (same as A's row 7);
  all delivery [HUMAN].
- Feasibility verdict: LOW-MEDIUM -- feasible engineering, worst
  verifiability and highest fragility; choose only if the literal
  modifier-drag ergonomics matter more than probe-provability.

## 4. Depth coverage (drag research RQ3)

## 5. Rotation scope (drag research RQ7c + deletion research sec.4 rows 1-3)

The 2026-10-18 decision text removes DIRECTION keys/buttons only;
rotation is NOT removed by the locked decision but MUST survive
somewhere. Evidence (committed records):

- 02-14-SUMMARY.md:92-96 -- the seed-42 TYR natural ring angle 79.606
  degrees fits NEITHER the <=30 parallel NOR the >=60 perpendicular
  window; translate-only placement formed NOTHING until a baked
  Rodrigues ring-alignment step was added. Orientation control is
  REQUIRED for solvability on pi-stacking levels, not just for feel.
- Reset-to-Grid preserves rotations (wizard.py:1030-1039) -- it is no
  substitute for a rotation input.
- Re-materialize rerolls orientation randomly (fragments carry no
  guaranteed ring orientation -- 02-14) -- also no substitute.

**PLANNER ANALYSIS (not a research receipt -- cites the thresholds.py
windows, PISTACK_ANGLE_TOL_DEG = 30.0):** Rotate-90-button-ONLY rotation
reaches just two distinct ring-plane angles mod 180 (theta, theta+90);
the pi-stacking windows leave gaps (30,60) and (120,150) -- e.g. a
45-degree start is UNFORMABLE by 90-deg quantization alone. So at least
one FINE rotation source (','/'.' keys and/or a dgrt drag-rotate) is
required for solvability on orientation-sensitive levels, not just for
feel. Deleting ALL fine rotation sets the OUT-OF-SCOPE flag (section 9).

Sub-rows, each with a proposed default:

- **R1 panel 'Rotate 90 deg' button (P8):** `rehome` (survives under its
  OWN 'Rotate:' panel header so the movement list proper keeps ONLY
  Toward-ligand -- verbatim-compliant) vs `delete` (strict reading).
  Proposed default: rehome.
- **R2 keyboard ','/'.' fine-rotation keys (K7/K8):** keep (they are
  keyboard rotate, not direction keys; the only zero-new-mechanism fine
  rotation) vs delete. Proposed default: keep.
- **R3 drag-rotate gesture (`dgrt`):** optional additional modifier slot
  (e.g. ctrl-left, currently camera pan) for drag-rotation -- NOTE the
  pivot divergence: dgrt pivots at the selection bbox center
  (editor_auto_origin=1 stock, Editor.cpp EditorPrepareDrag) vs our
