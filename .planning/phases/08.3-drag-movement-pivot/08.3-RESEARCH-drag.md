## 2. RQ answers

### RQ1 — PyMOL 2.5.0 mouse/drag event machinery

**(a) The button-mapping config surface.** `cmd.button(button, modifier, action)` (`pymol-src/modules/pymol/controlling.py:799-868`). Arguments are STRING enums only — button ∈ {left, middle, right, wheel, double_left, double_middle, double_right, single_left, single_middle, single_right} (`controlling.py:30-41`), modifier ∈ {none, shft, ctrl, ctsh, alt, alsh, ctal, ctas} (`:44-53`), and **action must be one of the 57 enumerated `but_act_code` strings** (`:57-123`) — it is lowercased, shortcut-matched (`but_act_sc.auto_err`, `:848`) and converted to an int code for the C call `_cmd.button(...)` (`:864`). **`cmd.button` CANNOT install an arbitrary command string** — there is no free-form action. The full drag-relevant action table (`controlling.py:57-123` → `layer1/ButMode.h:23-101`):

| action string | C code | meaning (source) |
|---|---|---|
| `rota` | 0 cButModeRotXYZ | camera orbit |
| `move` | 1 cButModeTransXY | camera pan |
| `movz` | 2 cButModeTransZ | camera dolly |
| `torf` | 16 cButModeTorFrag | torsion fragment (Editing ctrl-left) |
| `mova` | 28 cButModeMoveAtom | move ONE atom (Editing ctsh-left) |
| `roto`/`movo`/`mvoz` | 39/40/41 | rotate/move the picked OBJECT (matrix/TTT path) |
| `dgrt`/`dgmv`/`dgmz` | 36/37/38 RotDrag/MovDrag/MovDragZ | **drag-rotate / drag-translate / drag-depth of the armed drag selection** |
| `drgm`/`drgo` | 44/49 | click actions that PParses `cmd.drag("bymol/byobject (...)")` (`SceneMouse.cpp:263-280`) |

Mode profiles: `controlling.py:291-548` — 3-Button Viewing (`:320-348`): plain-left = `rota` (camera orbit), shift-left = `+Box`, ctrl-left = `move` (pan), ctsh-left = `sele`, alt-left = `move` (a DUPLICATE of ctrl-left pan). 3-Button Editing (`:349-377`): shift-left = `roto`, ctrl-left = `torf`, ctsh-left = `mova`, double-middle = `drgm`. `cmd.mouse(action)` switches profiles (`:609-686`); the docstring warns per-slot `button` changes are lost whenever the user cycles modes (`:823-825`).

**(b) The Dragging wizard — activation, replacement, dismissal (EMPIRICAL).** `cmd.drag(selection)` (`editing.py:1018-1076`): arms the C-side drag state, then `edit_mode(1)` (switches button profile to 3-Button Editing) and, unless the top wizard is already `Dragging`, calls `_self.wizard("dragging", old_button_mode)` (`editing.py:1067-1074`) → `_wizard(..., replace=0)` → `set_wizard(wiz, replace=0)` (`wizarding.py:30-52`) = a **PUSH**. ### RQ2 — Custom wiring INSIDE GameWizard: what can a wizard actually receive?

**The C→wizard channel inventory is FIXED** (`layer1/Wizard.h:47-59`, dispatch in `Wizard.cpp`): DoPick, DoSelect, DoKey, DoSpecial, DoScene, DoState, DoFrame, DoDirty, DoView, DoPosition. **There is NO drag/XY channel** — no wizard method ever receives raw mouse coordinates or deltas (the 08.2 source walk already established this; re-verified — `Wizard.cpp` has no other `WizardCallPython` sites). Candidate evaluation:

- **(i) a `do_drag` method the C layer calls on button-move — DOES NOT EXIST.** No such dispatch anywhere in `Wizard.cpp`/`SceneMouse.cpp`. The actual drag transforms happen entirely in C (`SceneDrag` → `EditorDrag`, `Editor.cpp:2136-2385`) and never consult the Python wizard.
- **(ii) `cmd.button` remap to a command string — DOES NOT WORK as imagined.** `cmd.button` accepts only the 57 enumerated action strings (RQ1a; `controlling.py:843-864`). There is no "run this command" action. The wizard_text button-code regex law (`tests/test_wizard_text.py:44`, `^cmd\.get_wizard\(\)\.[a-z_]+\(`) applies to PANEL codes (PParse'd at click time), not to mouse actions.
- **(iii) taking over a mouse-mode — VIABLE via the stock drag state, WITHOUT the stock wizard.** This is the recommended mechanism, now fully probe-proven:

**THE VIABLE MECHANISM (all receipts live, PyMOL 2.5.0):**

```python
# 1. ONE-TIME gesture map (at game activation; restore at cleanup):
cmd.button('left', 'shft', 'dgmv')   # shift-left-drag = translate the armed drag selection
#   optional extras: cmd.button('left', 'shft', 'dgrt')  # rotate (pick ONE of the two for shift-left)
#                    cmd.button('left', 'ctsh', 'dgmz')  # depth (toward/away viewer)
# 2. ON EVERY SUCCESSFUL PICK (end of do_pick, after the pk1 read):
cmd.select('_aam_drag_sele', obj)                    # selection-form name, NOT the object name
cmd.drag('_aam_drag_sele', wizard=0, edit=0)         # arm C-side drag; NO wizard install; NO mode switch
# 3. AT CLEANUP (Done/pop/replace):
cmd.drag()                                           # deactivate drag state
cmd.set('button_mode', saved_button_mode, quiet=1)   # profile-level restore
cmd.mouse()
```

Why each ingredient (source + probe):

1. **`wizard=0` avoids the Dragging wizard entirely.** `cmd.drag`'s wizard install is gated on the `wizard` kwarg (`editing.py:1061-1074`); `edit=0` skips the `edit_mode(1)` button-profile switch (`editing.py:1058-1060`). Probe: `C2 GameWizard STILL top-of-stack after wizard=0 arm PASS`, `C3 stack depth unchanged (1)`, `C8 button_mode NOT switched PASS`, `C9 GameWizard still receives picks after arm PASS` — **this closes the item ARCHITECTURE.md:169 flagged UNVERIFIED ("cmd.drag(sele, wizard=0, edit=0) ... drag-under-custom-wizard behavior is UNVERIFIED → requires a phase spike")** and ARCHITECTURE.md:375's open question.
2. **The arm must use a SELECTION name, never the object name.** `ExecutiveSetDrag` (`Executive.cpp:3208-3259`): an object name → `EditorSetDrag(G, obj, -1, ...)` → `DragSelection = -1` → `EditorDraggingObjectMatrix()` true → the C drag applies **ObjectCombineTTT (object MATRIX)** — the detector-blind, identity-breaking path (Pitfall-6c duality). A selection name → `_drag` selection built from it → `DragSelection >= 0` → `EditorDrag` else-branch applies **ObjectMoleculeTransformSelection — COORDINATE BAKING** (`Editor.cpp:2275-2281`, `ObjectMolecule.cpp:6207`). Probe 083B(5) + C5/C7: selection-arm gives `drag='_aam_aa01'`, `_drag` = all 19 atoms of the object (rigid body).
3. **The bake path preserves the identity-matrix law.** TransformSelection transforms CoordSet coordinates only; with `matrix_mode < 0` (default, SettingInfo.h:538 `REC_i(438, matrix_mode, ostate, -1, -1, 2)`) and no object TTT, the object matrix is untouched → stays identity. **Edge:** `EditorSetDrag` coerces to matrix-drag if the selection is full-state AND `matrix_mode >= 1` (`Editor.cpp:1824-1840`) — neutralize by setting the game object's `matrix_mode` to 0 at gamestart (`cmd.set('matrix_mode', '0', obj)` — probe E1 accepted; game objects are deleted at cleanup so no restore debt).
4. **The C drag math IS our movement law's math.** Per motion event (`SceneMouse.cpp:1479-1507`): `v2 = ((x-LastX)·vScale, (y-LastY)·vScale, 0)` in camera Å, then `MatrixInvTransformC44fAs33f3f(m_rotMatrix, v2, v2)` = **R^T conjugation** — the exact convention `wizard_core.view_camera_to_world` implements (`wizard_core.py:142-170`). Depth axis (`dgmz`): `v2 = (0, 0, -(y-LastY)·vScale)` (`:1487-1495`). Baking is incremental per event; no commit step.
5. **Re-arm after every pick — MANDATORY.** Probe 083B(1)/(2): **any pick clears the armed drag state** (`cmd.unpick()` alone suffices to clear it — `drag=''` after). The design therefore re-arms at the END of every `do_pick` (after the pk1 read — `EditorInactivate` deletes pk1..pk4, `Editor.cpp:1701-1740`, so arm AFTER reading, never before). Double-arm is idempotent (083B(4)). Re-arming also heals the `EditorActive` hazard (if the user ever enters edit-mode picking, `EditorActivate` sets `I->Active=true` and `EditorDrag` would take the fragment branch — `EditorSetDrag` starts with `EditorInactivate`, resetting Active=false, `Editor.cpp:1828`).
6. **What GameWizard can additionally observe:** the base class ships `event_mask_dirty=128` / `event_mask_view=256` / `event_mask_position=512` + `do_dirty()/do_view()/do_position()` hooks (`modules/pymol/wizard/__init__.py:6-15,58-74`), dispatched per render frame when the scene/view/center changed (`Wizard.cpp:100-131`, `Wizard.cpp:343-393`, called from `SceneUpdate`/`ExecutiveDrawNow`, `Scene.cpp:4589-4590`, `Executive.cpp:11181`). Enabling `event_mask_dirty` + a cheap `do_dirty()` (identity re-assert + `cmd.refresh_wizard()` — NO scene mutation, the base-class "BEWARE FEEDBACK!" warning) gives post-drag panel refresh + fail-closed matrix checking in the GUI. **These hooks did NOT fire in -cq headless** (probe F1/F2 count=0 — no draw loop in command mode), so hook behavior is a GUI-checkpoint item, not smoke-provable.
7. **Interaction with the user's mouse prefs (save/restore story):** there is **no per-slot read-back API** (`layer4/Cmd.cpp:6224` — only `{"button", CmdButton, METH_VARARGS}`; no `get_button`), so per-slot save/restore is IMPOSSIBLE via public API. The only story — the SAME one the stock Dragging wizard uses (`dragging.py:78-80`) — is profile-level: snapshot `button_mode` at activate (AFTER the set_wizard push, same ordering rationale as the msm snapshot, wizard.py contract 4), restore via `cmd.set('button_mode', saved)` + `cmd.mouse()` at cleanup, which re-applies the whole profile and thereby erases BOTH our remap and any user's pre-game per-slot customization (a documented stock limitation, `controlling.py:821-825`). Probe D2 proves the restore works.

### RQ3 — Drag math: pixel deltas → world-frame rigid translation

Exact PyMOL 2.5.0 mapping (source-verified, then numerically verified):

```
vScale [Å/px] = depth * GetFovWidth / viewport_height_px        (Scene.cpp:3550-3558)
GetFovWidth   = 2 * tan(field_of_view * pi / 360)               (Scene.cpp:5613-5617; fov default 20.0, SettingInfo.h:237)
depth         = SceneGetRawDepth(G, v1) with v1 = m_view.m_origin (the drag path, SceneMouse.cpp:1481-1482)
              = -m_pos[2] = -cmd.get_view()[11]                 (MV = T(pos)·R·T(-origin), Scene.cpp:3475-3481;
                                                                 MV·origin = pos ⇒ depth = -pos[2]; ortho same, Scene.cpp:3520-3522)
world_delta   = R^T · (dx_px·vScale, dy_px·vScale, 0)           (SceneMouse.cpp:1492-1502)
```

Probe receipts: at the real seed-42 game view (P1's captured post-start view), probe G measured `viewport=640x480 fov=20 depth(-view[11])=97.2456 → A_per_px=0.07145`, and the WSL pure-math probe reproduced it exactly (`C1 formula matches probe G measurement PASS calc=0.07145`) plus the R^T equivalence with `view_camera_to_world` at full SO(3) (`C2 dev=0.00e+00`).

**Gameplay sanity at the default view:** one `GRID_SPACING` cell (8.0 Å, `generator.py:110`) ≈ **112 px** of drag; a TOWARD-like 2.5 Å ≈ 35 px (640×480 headless viewport; a taller real window scales proportionally — 1080 px height ⇒ ~50 Å per 1000 px... i.e. ≈ 0.032 Å/px, one cell ≈ 253 px). The scale is depth-normalized (the same `vScale` the renderer uses), so the object tracks the cursor 1:1 at the view-origin depth. Known approximation: `vScale` is evaluated at the **view origin**, not at the dragged AA — at the game's default view the AA grid sits ~9 Å nearer the camera than the origin (~97 vs ~106 Å depth ⇒ ~9% faster-than-cursor); imperceptible for play, recorded for honesty. No pixel-per-Å constant belongs in our code — read `get_view()[11]`, `get_viewport()`, `field_of_view` live if a wizard-side programmatic path is shipped (SMOKE-provable; see RQ6).

**Vertical-axis (depth) question:** view-plane drag (`dgmv`) cannot move the AA toward/away from the viewer. Depth coverage options: (1) **Toward-ligand already moves along the 3D centroid-to-centroid line** (`wizard.py:729-753`) — it is depth-capable by construction; (2) a depth drag (`dgmz` on a second modifier) for fine depth trim; (3) the orbit-then-drag trick (orbit the camera ~90° so the depth axis becomes screen-plane, then drag) — works with plain camera tools and any view-plane drag. Recommendation: ship (1) always; make (2) a menu sub-choice; document (3) in Phase-9 help. (2)+(3) make final-Å depth trim reachable without any new concept.

### RQ4 — Rigid-body + baked-coord constraints: does drag route through the sanctioned seams?

**The C-side drag (recommended mechanism) bakes by construction, but bypasses wizard code — the invariant must be re-asserted post-hoc.** Source chain: armed `_drag` selection covering exactly the picked object's atoms → `EditorDrag` MovDrag/RotDrag cases with `DragSelection >= 0` → `ObjectMoleculeTransformSelection(objMol, state, I->DragSelection, m, ...)` (`Editor.cpp:2193-2197, 2237-2241, 2275-2281`) → **all selected atoms translated/rotated identically (rigid), stored coordinates baked, object matrix untouched → identity invariant holds**. The wizard's fail-closed `_assert_identity(obj)` (`wizard.py:620-638`) remains the enforcement: call it (a) in the GUI via the `do_dirty` hook after drag motions (cheap, idempotent, no scene mutation), (b) at every subsequent pick, (c) inside Confirm (already implicit — detection reads live coords; the assert makes any matrix corruption surface loudly), (d) in `reset_grid`'s existing post-assert sweep (`wizard.py:1048-1053`).

**If a wizard-side programmatic path is ALSO shipped** (`drag_move(dx_px, dy_px)` — see RQ6), it routes through the EXISTING sanctioned seam verbatim: compute `w = view_camera_to_world(cmd.get_view(), (dx·s, dy·s, 0))` then `cmd.translate([s·w...], obj, state=1, camera=0)` + `_assert_identity` — i.e. drag is just an analog source of `(dx_world, dy_world, 0)`-style vectors into the `_nudge_cam_impl` pattern (`wizard.py:677-688`), with `_require_playing()` first and `_guard()` wrapping.

**No step-quantization needed; asserts unaffected.** NUDGE_STEP quantization was a discrete-press UX choice, not a law: the detector consumes continuous coordinates against continuous thresholds; nothing in `tests/` or the detector pins per-move step sizes for free moves. `placement._assert_pose`/`POSE_TOLERANCE` (`placement.py:84, 199-208`) applies to scripted `place_aa` replays only — free moves were never pose-asserted (only identity-asserted). Float32 accumulation from many tiny bakes is inside the documented budgets (02-14: distances ≤ 5e-6 Å / angles ≤ 3e-4 deg, observed drift 2.61e-9 Å / 0.0 deg under whole-scene rotation). The identity matrix is untouched by translates; rotation-bakes keep it too (SMOKE-06 Q1 precedent). The one NEW hazard the identity assert covers: the matrix-drag duality (RQ2 item 3) — if any path ever coerces to ObjectCombineTTT, the next assert FAILS CLOSED naming the object. That is the designed behavior.
